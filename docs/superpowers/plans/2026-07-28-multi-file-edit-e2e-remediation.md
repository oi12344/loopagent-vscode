# 多文件修改 E2E 测试与整改清单

## 测试目标

验证 DeepSeek 动态工作流能否通过两个无依赖的 `executor` 子智能体并行创建不同文件，并在父智能体中核验结果；同时检查执行计划、修改卡片、历史恢复和文件落盘行为。

## 测试场景

- 模型：真实 DeepSeek API。
- 工作流：一个动态执行图，包含两个无依赖 `executor` 节点，不包含 `reviewer`。
- 节点 A：通过 `applyEdit` 创建 `.loopagent-e2e-a.txt`。
- 节点 B：通过 `applyEdit` 创建 `.loopagent-e2e-b.txt`。
- 父智能体：通过 `readFile` 核验两个文件并输出总结。
- UI 证据：`.artifacts/multi-file-edit-e2e.png`。

## 实测结论

本次 E2E 未通过。执行图和两个修改卡片可以显示，但修改没有可靠落盘，所谓并行执行实际被串行化；切换会话后，执行计划和修改卡片丢失。

## 必须整改

| 优先级 | 问题 | 实测证据 | 根因 | 验收标准 |
| --- | --- | --- | --- | --- |
| P0 | `applyEdit` 报告成功但文件内容未落盘 | 两个节点均返回成功，`readFile` 能读到目标内容，但磁盘上的两个文件均为 0 字节 | `EditPreviewService.apply()` 只调用 `workspace.applyEdit()`，没有保存变脏的文本文档 | 工具返回成功前，相关文件在磁盘上具有目标内容；关闭或重载 VS Code 后内容仍存在 |
| P0 | 父智能体产生错误的成功结论 | 最终总结称两个文件内容完全一致，实际磁盘为空 | `readFile` 读取了 VS Code 的脏缓冲区，未验证持久化状态 | 结果状态明确区分“已写入缓冲区”和“已保存”；只有磁盘持久化成功后才能报告修改完成 |
| P1 | 图上无依赖的执行节点没有并行运行 | 节点 B 在节点 A 完成后才进入 `running` | `workflowOrchestrator.schedule()` 用 `hasRunningExecutor` 明确限制同时只能运行一个 `executor` | 两个无依赖且工具互不冲突的执行节点同时进入运行态；冲突文件仍按资源锁串行化 |
| P1 | 历史恢复丢失执行过程 | 新建会话后再打开历史，仅恢复 1 条用户消息和 1 条助手消息，执行计划为 0，修改卡片为 0 | `conversationRestored` 只把聊天消息映射为 `turns`，工作流事件和编辑通知没有持久化或恢复 | 切换会话或重载后，计划、节点状态、修改文件清单和可用的撤销状态仍可查看 |
| P1 | “保留”并不保存文件 | 点击两个修改卡片的“保留”后，磁盘文件仍为 0 字节 | `dismissAppliedEdit()` 只从 React 状态移除卡片 | 若按钮含义是接受修改，应执行保存并显示结果；若只关闭提示，应改名并明确文件仍未保存 |
| P1 | 大型多文件图存在错误完成语义 | 补充测试中的 8 个无依赖执行节点有 5 个失败且无源码修改落地，但结果仍将全部节点列入 `completedNodes` | 完成集合和终态统计未严格区分成功、失败及未落盘 | 任何失败节点都不能出现在成功完成集合；父智能体必须基于真实终态生成总结 |

## UI 整改

| 优先级 | 问题 | 建议与验收标准 |
| --- | --- | --- |
| P1 | 助手在文件真正保存前显示 3/3 完成 | 将状态拆分为“执行完成”“等待确认”“已保存”，最终完成只对应可持久化结果 |
| P1 | 修改卡片把之前的对话挤出可视区域，看起来像对话消失 | `.app-shell` 只定义三行，但卡片出现后形成四个顶层区块；卡片自动高度会把 `.chat-log` 的 `minmax(0, 1fr)` 压缩到接近 0。将修改区纳入明确的受限布局或聊天滚动区，设置最大高度并允许卡片内部滚动；无论出现多少卡片，聊天区都必须保留可见高度且能滚回此前消息 |
| P2 | 单文件修改卡片仍显示搜索框 | 文件数量低于可配置阈值时隐藏搜索框 |
| P2 | “保留/撤销”文案语义不清 | 使用“保存并保留/撤销修改”，或把纯关闭操作命名为“关闭提示” |
| P2 | 助手建议执行 `rm`，与界面的撤销能力冲突 | 总结优先引导使用产品内撤销动作，不主动输出删除命令 |
| P2 | 历史会话在当前调试窗口中显示原始 Markdown 符号 | 在确认加载最新 webview bundle 后增加 E2E 断言，确保标题、表格和代码块不会显示 `##`、竖线或围栏符号 |

## 测试基础设施整改

| 优先级 | 问题 | 建议与验收标准 |

## 已通过的基线检查

- `npm run compile`
- `npm run typecheck`
- 5 个相关测试文件，共 97 个测试用例

这些检查说明当前编译和已有单元测试通过，但不足以覆盖真实 VS Code 编辑缓冲区、磁盘保存及历史恢复行为。

## 建议修复顺序

1. 先修复 `applyEdit` 的保存语义和成功状态，避免数据丢失与错误成功结论。
2. 再移除 `executor` 全局串行限制，改为按工具或文件冲突控制并发。
3. 持久化并恢复工作流计划、节点终态和编辑通知。
4. 最后收敛修改卡片布局、按钮文案和历史 Markdown 展示。
