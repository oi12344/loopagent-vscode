# Headroom 0.31 平衡增强升级设计

## 背景

当前主机通过 `C:\Users\79905\.codex\headroom_start_proxy.ps1` 启动 Headroom，并由 `127.0.0.1:8787` 承接 Codex 请求。2026 年 7 月 10 日的实时核验结果如下：

- 当前运行版本为 `0.27.0`，PyPI 最新正式版为 `0.31.0`。
- 当前会话整体输入 token 节省率约为 `11.8%`，被压缩请求的平均压缩率为 `20.2%`。
- 当前会话没有代理请求失败，但压缩执行器曾报告泄漏线程和较长的单次运行时间。
- 当前启动脚本使用 `target_ratio=0.25`、`protect_recent=3`、`max_items=20`，不压缩 system/user 消息。

仓库已有 `2026-07-10-headroom-40-percent-low-cpu-tuning-*` 文档，其运行路径为 `C:\Users\msi\.codex\...`。这些文件记录另一主机或用户配置的历史结果，不能替代本设计对当前 `C:\Users\79905\.codex\...` 运行环境的核验。

## 目标

1. 将当前主机的 Headroom 从 `0.27.0` 升级到 `0.31.0`。
2. 以平衡增强策略将整体输入 token 节省率目标提高到约 `30%`。
3. 把 `24%` 作为显著改善线，即当前约 `12%` 基线的两倍。
4. 保持真实 Codex 请求零失败，并限制压缩延迟、CPU 并发和泄漏线程风险。
5. 保留可在一次切换流程内恢复的 `0.27.0` 环境和启动脚本。

压缩率受请求模型、上下文结构、前缀冻结和受保护消息比例影响，`30%` 是调优目标而不是无条件保证。达到安全边界后仍低于目标时，应记录实际上限，不以牺牲上下文完整性或连接稳定性换取数字。

## 非目标

- 不修改 LoopAgent VS Code 扩展源码。
- 不修改 Codex 的 provider 地址或上游 API 地址。
- 不压缩 system/user 消息。
- 不启用 `agent-90`、`FORCE_KOMPRESS` 或第二个在线压缩侧车。
- 不在正式代理工作时并行运行 `8788` 压缩基准。
- 不删除旧 `0.27.0` 虚拟环境。

## 方案选择

采用隔离安装后切换：

- 保留 `C:\Users\79905\.codex\headroom-win` 作为旧 `0.27.0` 环境。
- 新建 `C:\Users\79905\.codex\headroom-win-031`，安装 `headroom-ai[proxy]==0.31.0`。
- 新环境只做离线版本、依赖和命令检查，不在旧代理运行时绑定额外代理端口。
- 通过候选启动脚本、带时间戳备份和单次切换流程，把正式 `8787` 从旧环境切到新环境。

不采用原地升级，因为依赖变更后难以快速恢复；不直接使用官方 `balanced` 配置，因为其 `target_ratio=0.30`、`protect_recent=4` 等默认值比当前配置更保守，无法支撑显著提高压缩率的目标。

## 组件与边界

### 旧运行环境

`C:\Users\79905\.codex\headroom-win` 保持不变，只承担回滚。升级流程不得在该环境中执行 `pip install --upgrade`。

### 新运行环境

`C:\Users\79905\.codex\headroom-win-031` 只包含新的 Headroom 及代理依赖。切换前至少验证：

- `headroom --version` 报告 `0.31.0`。
- `python -m pip check` 通过。
- 代理命令及必要 Python 模块可导入。
- `agent-savings` 能渲染配置，但不启动第二个代理。

### 正式启动脚本

开机启动快捷方式继续调用 `C:\Users\79905\.codex\headroom_start_proxy.ps1`。切换只修改该脚本中的 Headroom 可执行文件路径和明确批准的压缩参数，不修改快捷方式，也不新增另一条长期启动链。

候选脚本必须先在临时路径完成 PowerShell 语法解析和配置断言。正式替换前创建带时间戳的原始脚本备份，并记录新旧文件 SHA256。

## 请求数据流

升级前后数据流保持不变：

```text
Codex
  -> http://127.0.0.1:8787/v1
  -> Headroom proxy
  -> 现有上游 API
```

新虚拟环境、压缩参数和执行器上限属于 Headroom 内部实现，不改变 Codex 与代理之间的接口。切换必须在一个 PowerShell 流程内完成，确保工具调用返回后 `8787` 已经由新代理承接，或者已经自动恢复旧代理。

## 平衡增强配置

初始配置使用显式环境变量，不依赖命名 profile 的隐式默认值：

```powershell
$env:HEADROOM_MODE = "token"
$env:HEADROOM_MIN_TOKENS = "120"
$env:HEADROOM_TARGET_RATIO = "0.20"
$env:HEADROOM_PROTECT_RECENT = "2"
$env:HEADROOM_MAX_ITEMS = "15"
$env:HEADROOM_SMART_CRUSHER_COMPACTION = "1"
$env:HEADROOM_COMPRESS_USER_MESSAGES = "0"
$env:HEADROOM_COMPRESS_SYSTEM_MESSAGES = "0"
$env:HEADROOM_FORCE_KOMPRESS = "0"
$env:HEADROOM_ACCURACY_GUARD = "strict"
$env:HEADROOM_PROTECT_ANALYSIS_CONTEXT = "1"
$env:HEADROOM_COMPRESS_WORKERS = "4"
$env:HEADROOM_COMPRESSION_MAX_WORKERS = "4"
$env:HEADROOM_COMPRESSION_TIMEOUT_SECONDS = "15"
```

取舍如下：

- `target_ratio=0.20`、`max_items=15` 和 `protect_recent=2` 增强对较旧工具结果的压缩。
- `min_tokens=120` 避免为很小的内容支付压缩开销。
- system/user 消息、分析上下文和最近两轮继续受保护。
- 4-worker 全局上限和 15 秒等待上限限制 CPU 争用和超时任务堆积。
- `strict` 准确性保护和非强制 Kompress 保持稳定性优先。

## 调优阶梯

首次切换后观察至少 10 个真实 Codex 请求。统计时记录模型分布、前缀冻结数量和可压缩请求数量，避免把模型组合变化误认为配置收益。

1. 若整体节省率达到 `30%`，停止调优。
2. 若整体节省率达到 `24%` 但低于 `30%`，视为显著改善，保持当前配置并记录未达到目标的原因。
3. 若整体节省率低于 `24%` 且所有安全指标通过，单独将 `HEADROOM_MAX_ITEMS` 从 `15` 调为 `12`，重启后重新观察至少 10 个请求。
4. 若仍低于 `24%` 且安全指标继续通过，再单独将 `HEADROOM_TARGET_RATIO` 从 `0.20` 调为 `0.18`，重启后重新观察至少 10 个请求。
5. `max_items=12` 和 `target_ratio=0.18` 是本设计的下限。仍未达到显著改善线时停止加压，保留 system/user 和分析上下文保护，并记录实际可达到的上限。

每次只改变一个参数。出现失败、队列超时、持续 CPU 占用、泄漏线程增长或延迟越界时，不进入下一阶梯。

## 切换与回滚

### 切换前

记录以下证据：

- 当前版本、`/health`、`/stats` 和 `8787` 端口所有者。
- 当前会话请求数、失败数、整体节省率和被压缩请求平均压缩率。
- 当前启动脚本内容摘要、SHA256 和备份路径。
- 开机启动快捷方式的目标、参数和工作目录。
- 旧虚拟环境中的 `headroom.exe` 可执行且版本仍为 `0.27.0`。

不得在输出、文档或日志摘要中记录 API key、访问令牌或其他凭据。

### 正式切换

1. 精确定位占用 `8787` 的旧代理进程链，不停止 Headroom MCP 或其他无关 Python 进程。
2. 停止旧代理，原子替换已经验证的候选启动脚本。
3. 通过正式启动脚本启动 `0.31.0`。
4. 在 60 秒内验证端口、`/livez`、`/health`、`/stats`、版本和运行配置；无凭据访问 `/v1/models` 时应返回上游鉴权错误，而不是连接失败或 `502`。
5. 验证当前 Codex 会话能继续产生真实请求。

### 自动回滚条件

切换进程可以直接观察的以下任一条件触发自动脚本回滚：

- 60 秒内 `8787` 未监听。
- `/livez` 不返回 `200`。
- `/health` 版本不是 `0.31.0`。
- 启动脚本或运行配置与批准值不一致。
- `/v1/models` 返回连接失败或 `502`，而不是预期的上游鉴权响应。

回滚恢复原启动脚本，通过旧环境重新启动 `0.27.0`，并再次验证端口、健康状态和真实请求。`/readyz` 可能受上游探活影响，不作为唯一回滚依据。

切换进程结束后，首个真实 Codex 请求失败、优化延迟越界或资源指标恶化无法由已结束的切换进程自动观察。这些情况触发立即运行同一回滚入口，不继续调参。实施前必须先验证该回滚入口能够恢复备份脚本并启动旧环境，避免故障发生后再拼接恢复命令。

## 验收标准

### 版本与连接

- 正式代理版本为 `0.31.0`。
- `127.0.0.1:8787` 只有一个正式代理监听器。
- `GET /livez` 返回 `200`，`GET /health` 和 `GET /stats` 可读取。
- 开机启动快捷方式仍指向正式启动脚本。
- 真实 Codex 请求失败数为 `0`。

### 配置与资源

- `/health` 报告批准的压缩参数。
- 压缩执行器全局 worker 数为 `4`，来源为显式配置。
- `queue_timeouts_total=0`，观察结束时 `running=0`、`in_flight=0`。
- 3 秒空闲窗口的 Headroom CPU 时间增量为 `0`。
- 泄漏线程计数不随观察窗口持续增长。

### 压缩与延迟

- 每个配置窗口至少包含 10 个真实 Codex 请求。
- 目标整体输入 token 节省率约为 `30%`。
- `24%` 及以上视为相对当前约 `12%` 基线的显著改善。
- Headroom `optimization_latency_ms` P95 不超过 `500ms`。
- 记录被压缩请求平均压缩率、整体节省率、模型分布、前缀冻结和不可压缩请求，不混用不同指标。

压缩率低于目标但稳定性指标全部通过时，不自动回滚版本；按调优阶梯处理并记录结果。安全指标失败时，稳定性优先于压缩率。

## 测试与验证产物

实施阶段需要产生以下验证结果：

- 新环境的版本、依赖和导入检查。

- 端口、进程、线程、队列和空闲 CPU 检查。
- 启动快捷方式复核和旧环境回滚可用性检查。
